### Buffer Format

The driver treats the IOCTL system buffer as a pseudo-IRP structure, accessing fields by their offsets in `_IRP`. The effective layout is:

```c
typedef struct {
    DWORD   Command;   // [+0x00] command code (maps to IRP.Type/Size as DWORD)
    DWORD   Length;    // [+0x04] byte count   (maps to IRP.AllocationProcessorNumber)
    PVOID64 Address;   // [+0x08] kernel VA / port number (maps to IRP.MdlAddress)
    BYTE    Data[];    // [+0x10] read result / write payload (maps to IRP.Flags onward)
} CH367_CMD;
```

## Vulnerability Details

### Primary: Arbitrary Kernel Virtual Address Read/Write (CVE-class: LPE)

**Commands 24 and 28** in `CH367_DispatchDeviceControl` pass the usermode-supplied 64-bit `Address` field (`buffer[8..15]`) directly as source/destination to kernel-mode `memcpy` — with no address validation, no `ProbeForWrite`, and no bounds checking on the length field.

**Command 24 — Kernel Read** (`0x117C0` + case 23, address `0x11CE1`):
```c
// buffer[8..15] = any kernel virtual address
// buffer[4..7]  = byte count
qmemcpy(&SystemBuffer[0x10], (void *)buffer->Address, buffer->Length);
// Result returned to usermode in the output buffer at offset 0x10
```

**Command 28 — Kernel Write** (`0x117C0` + case 27, address `0x11D0B`):
```c
// buffer[8..15] = any kernel virtual address
// buffer[4..7]  = byte count
// buffer[16+]   = data to write (from usermode input)
qmemcpy((void *)buffer->Address, &SystemBuffer[0x10], buffer->Length);
```

**Root cause:** The driver author intended these commands for internal DMA buffer management (staging buffer access at `DevExt+88` and `DevExt+96`), but commands 24/28 operate on the raw pointer from the IOCTL buffer rather than a bounded offset. No security boundary is enforced.

**Impact:**
- Any local user can read from and write to any valid kernel virtual address
- Enables trivial local privilege escalation (SYSTEM token injection, disabling PPL, etc.)
- No exploit mitigations are bypassed — this is a direct kernel R/W primitive

### Secondary: Arbitrary I/O Port Read/Write

Commands 16–22 and 39–40 use `buffer[8]` (truncated to 16 bits) as the x86 I/O port address for `IN`/`OUT` instructions. This exposes all hardware I/O ports (0x0000–0xFFFF) to usermode, bypassing the IOPL restriction.

Notable exploitable port ranges: PCI configuration mechanism ports (0xCF8/0xCFC), SMI triggers, PMC/MSR-adjacent ports.

### Tertiary: Arbitrary Physical Address Mapping

Command 7 (case 6, `0x119C7`) calls:
```c
PhysicalAddress.QuadPart = (UINT32)buffer->Address;  // usermode-supplied
MmMapIoSpace(PhysicalAddress, 0x8000, MmNonCached);  // maps 32 KB
```
The physical address is the 32-bit truncation of the usermode-supplied `Address` field. The mapped VA is stored at `DevExt+104`. On its own this is limited (32-bit PA only, no direct R/W path in the command set), but combined with an accessible physical range it allows MMIO-level hardware manipulation.

## Exploitation

### Attack Vector

1. Enumerate the device interface by GUID `{51AD4462-8E54-4D54-A019-133B59D3AFA4}`
2. Open device with `CreateFile` (no special privileges needed)
3. Send IOCTL `0x223CD8` with command 24 to read arbitrary kernel memory
4. Send IOCTL `0x223CD8` with command 28 to write arbitrary kernel memory
5. Escalate to SYSTEM via EPROCESS token swap

### LPE via Token Swap (Windows 10 2004+ / Windows 11)

```
1. NtQuerySystemInformation(SystemModuleInformation) → ntoskrnl base address
2. Resolve PsInitialSystemProcess export offset → kernel VA
3. KernelRead(PsInitialSystemProcess, 8) → System EPROCESS pointer
4. KernelRead(SystemEPROCESS + 0x4B8, 8) → System Token (EX_FAST_REF)
5. NtQuerySystemInformation or EPROCESS walk → current EPROCESS pointer
6. KernelWrite(CurrentEPROCESS + 0x4B8, 8, SystemToken) → SYSTEM privileges
7. CreateProcess("cmd.exe") → SYSTEM shell
```

## Summary

CH367WDM64.sys is a PCI serial/parallel port controller driver from WinChipHead. Its `IRP_MJ_DEVICE_CONTROL` handler exposes a single IOCTL (`0x223CD8`, METHOD_BUFFERED, FILE_ANY_ACCESS) that dispatches 40+ internal commands. Commands 24 and 28 are a direct kernel memory read and write primitive: they pass the 64-bit `Address` field from the usermode IOCTL buffer straight into `memcpy` as source and destination respectively, with no validation. The device is accessible to any local user. This is a straightforward local privilege escalation to SYSTEM with no exploit mitigations to bypass.
